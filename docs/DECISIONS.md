# Architecture Decision Records (ADR)

各エントリは「決定 / 背景 / 選択肢 / 選択理由 / トレードオフ」の形式で記述する。

## ADR-001: リポジトリを Godot プロジェクトとして新規開始する

- **決定**: 既存の Minecraft Paper プラグイン（CropSneakGrowth, Java/Maven）を削除し、
  同一リポジトリを Godot 4.3 の Arena 3v3 プロジェクトとしてゼロから構築する。
- **背景**: 本リポジトリには元々 `pom.xml` と Bukkit プラグインのソースが存在しており、
  依頼された「AAA級 3v3 ヒーローシューター（Godot）」の仕様とは無関係だった。
- **選択肢**:
  1. 別リポジトリ作成を要求する
  2. 既存コードを残したまま Godot プロジェクトを共存させる
  3. 既存コードを削除して Godot プロジェクトとして再スタートする
- **選択理由**: ユーザーに確認したところ「このリポジトリで新規に Godot プロジェクトを開始する」
  ことが明示的に承認されたため、3 を採用。共存（2）は言語・ビルドツールが全く異なり
  混乱の元になるため却下。
- **トレードオフ**: 元の Minecraft プラグインの履歴は git log 上に残るが、
  ワーキングツリーからは削除される。

## ADR-002: エンジンバージョンを Godot 4.3 stable に固定する

- **決定**: 開発・CI で使用する Godot バージョンを **4.3.stable.official** に固定する。
- **背景**: 第9章の「API 検証プロトコル」に従い、実機バージョンでの検証が必須。
  ネットワーク経由で取得可能な安定版として 4.3 系を採用した。
- **選択肢**: 4.2 系 / 4.3 系 / 4.4 系（開発時点で 4.3 が広く使われる安定版）
- **選択理由**: `LookAtModifier3D` など一部の新APIは 4.4 以降で追加されているが、
  4.3 は Forward+ / SDFGI / CompositorEffect / MultiplayerSynchronizer のデルタ同期など
  本プロジェクトが必要とする主要機能をすべて備えた安定版であるため採用。
- **トレードオフ**: `LookAtModifier3D` が使えないため、Phase 2 のエイムオフセット実装は
  `SkeletonIK3D` または独自の `SkeletonModifier3D` 継承クラスで代替する必要がある
  （`docs/ENGINE_BASELINE.md` 参照）。

## ADR-003: gdUnit4 をテストフレームワークとして採用する

- **決定**: ユニット/統合テストフレームワークとして **gdUnit4** を採用する。
- **背景**: 第8章で gdUnit4 または GUT のいずれかの使用が指示されている。
- **選択肢**: gdUnit4 / GUT
- **選択理由**: gdUnit4 は `--headless` での CLI 実行（`GdUnitCmdTool.gd`）が
  CI パイプラインと親和性が高く、Godot 4.x 系のアクティブなメンテナンスがあるため採用。
- **トレードオフ**: addon の実体はネットワーク取得が必要になる場合があり、
  Phase 0 時点ではダミーテストランナー（`tools/ci_test.sh`）で
  `--check-only` 相当の検証を先行させ、gdUnit4 本体の導入は
  取得可否を確認したうえで追って行う。

## ADR-004: HeroBase のコンポーネント初期化は `initialize()` 明示呼び出しで行う

- **決定**: 各コンポーネント（HealthComponent, MovementComponent 等）は `_ready()` 内で
  自身の初期値を確定させず、`HeroBase._ready()` から明示的に `initialize(...)` を
  呼び出すことで初期化する。
- **背景**: Godot の `_ready()` は子ノードが親より先に呼ばれる（ボトムアップ）。
  `HealthComponent._ready()` が `hero_data.base_health` を参照する構造だと、
  `HeroBase._ready()` がまだ `hero_data` を伝搬する前にコンポーネント側の初期化が
  完了してしまい、常にデフォルト値が使われるバグを生む。
- **選択肢**:
  1. `_ready()` の実行順序に依存させる
  2. 明示的な `initialize()` メソッドを各コンポーネントに持たせ、親から呼ぶ
- **選択理由**: 2 を採用。暗黙の実行順序への依存は「Godot API を推測で書くな」という
  第9章の精神に反する（実測せず直感的な順序を仮定するのは同種の誤り）ため、
  明示的な初期化 API で確実性を担保する。
- **トレードオフ**: コンポーネントごとに `initialize()` を1つ増やす必要があるが、
  ヒーロー追加時にはこの呼び出し規約自体は変更不要（HeroBase 側のみで完結）。

## ADR-005: `AbilityBase` と `AbilityData` を単一の `AbilityData` Resource に統合する

- **決定**: 指示書 3.2 章の `AbilityBase (Resource)` と 3.3 章の `AbilityData` は
  同一概念の重複表現とみなし、`AbilityData`（`src/gameplay/abilities/ability_data.gd`）
  ひとつに統合する。能力の実行ロジックは `AbilityData.execution_scene`
  （`PackedScene`）が指す Node 側に持たせる。
- **背景**: 指示書内でクラス名が2箇所で異なって参照されており、両方を別クラスとして
  実装すると意味のない委譲層が増え、「無駄な抽象化を避ける」という第0章の方針に反する。
- **選択肢**: 1. 両クラスを別々に実装し継承関係を作る　2. 単一の Resource に統合する
- **選択理由**: 2 を採用。データ（クールダウン等）と実行（Node）を分離する設計意図は
  `execution_scene` フィールドだけで十分に表現できる。
- **トレードオフ**: 指示書の想定するクラス名 `AbilityBase` は存在しないため、
  将来指示書を参照する際はこの ADR を参照すること。

## ADR-006: `GameFeelTuning` / `NetConfig` はヒーロー単位ではなくグローバル Resource として `preload` する

- **決定**: `MovementComponent` 等がゲームフィール定数を参照する際は、
  `HeroData` 経由ではなく `res://data/tuning/game_feel.tres` を `const` として
  直接 `preload` する。
- **背景**: 第4章の `GameFeelTuning` は「全ゲームフィール定数」であり、
  ヒーローごとに異なる値を持つ設計ではない。`HeroData` に含めると
  ヒーロー追加のたびに同じ値を再指定する羽目になり、単一情報源の原則に反する。
- **選択肢**: 1. `HeroData` にチューニング参照を持たせる　2. コンポーネント側で直接 `preload`
- **選択理由**: 2 を採用。Autoload 数の上限（5個）を消費せず、かつ Resource の
  キャッシュにより同一インスタンスが共有されるため、データの一意性も保たれる。
- **トレードオフ**: 実行時にチューニング値をホットリロードする場合は
  `preload` ではなく `load` への変更が必要になる（Phase 5 のデバッグ機能で再検討）。

## ADR-007: MovementSimulation は「速度計算の純粋関数」に限定し、衝突解決は呼び出し側が担う

- **決定**: `MovementSimulation.step()` は `MoveState`/`InputCommand`/`MoveConfig` のみを
  引数に取り、新しい `MoveState` を返す静的関数として実装する。実際の `move_and_slide()`
  呼び出しと `is_on_floor()` の反映は `HeroBase._physics_process()` が行う。
- **背景**: 第5.3章は「サーバーとクライアントは物理的に同一のこのコードを呼ぶ」ことを
  要求する。しかし Godot の衝突解決（`move_and_slide`）は `CharacterBody3D` インスタンス
  固有の状態（コリジョン形状・物理空間）に依存するため、真の意味での純粋関数には
  できない。
- **選択肢**: 1. 衝突解決も含めて完全に自作の物理シミュレーションを書く
  2. 速度・タイマー類の計算のみを純粋関数化し、衝突解決は Godot の物理エンジンに委ねる
- **選択理由**: 2 を採用。自作物理エンジンは AAA の「妥協禁止」の精神には合致するが、
  費用対効果が悪く、Godot の `CharacterBody3D` の枯れた衝突解決を捨てる理由がない。
  決定論テスト（`tests/unit/test_movement_simulation.gd`）は衝突を伴わない区間で
  ビット一致を検証することで、この境界線を明示している。
- **トレードオフ**: 衝突が絡む区間（壁ずり・階段等）の完全なビット一致は
  Godot の物理エンジン自体の決定性に依存する。Phase 4 のリコンサイルテストで
  実際のネットワーク環境下での挙動を別途検証する。

## ADR-008: カメラリグは `top_level = true` で親のTransformから独立させ、Yのみ指数平滑化する

- **決定**: `CameraRigComponent`（`SpringArm3D` 継承）は `top_level = true` を設定し、
  毎フレーム `global_position` を手動で計算する。X/Z はヒーロー本体に瞬時追従させ、
  Y のみ `1 - exp(-delta / step_smoothing_seconds)` で平滑化する。
- **背景**: 第4.2/4.3章は「段差でカメラが跳ねないよう、カメラだけY座標をスムーズ追従
  させる」ことを要求する。通常の親子付けでは `CharacterBody3D` の階段上りによる
  瞬間的なY変化がカメラにそのまま伝播してしまう。
- **選択肢**: 1. 通常の子ノードのままY方向のみ別ロジックで補正する
  2. `top_level` でTransform継承を切り、全軸を手動制御した上でYだけ平滑化する
- **選択理由**: 2 を採用。`top_level` は Godot 4.3 で実測確認済み（`Node3D` の
  標準プロパティ）であり、親のRotationにカメラが引きずられる問題も同時に回避できる。
- **トレードオフ**: 手動での位置追従になるため、将来的に体の傾き（ロール）等を
  カメラに反映したくなった場合は明示的に計算式へ追加する必要がある。

## ADR-010: gdUnit4 CLI (`--script`モード) 終了時の "resources still in use" は既知のエンジン挙動として扱う

- **決定**: `godot --headless -s addons/gdUnit4/bin/GdUnitCmdTool.gd` で
  `tests/unit/test_hero_data_driven.gd` を実行すると、プロセス終了時に
  `WARNING: ObjectDB instances leaked at exit` / `ERROR: N resources still in use at exit`
  が出力される。調査の結果、**リークとして報告されるインスタンスは全て `GDScript`
  （スクリプトのクラス定義そのもの）であり、`HeroBase`/`WeaponComponent`/`DamageInfo`
  等の実際のゲームプレイオブジェクトは1件も含まれていない**ことを確認した
  （`--verbose` 出力を全件 grep し、自作クラス名が一切ヒットしないことで検証済み）。
  これは Godot の `--script` エントリポイント経由の短命プロセス実行で、
  `class_name` を多用した相互参照の多いスクリプト群を読み込んだ際に発生する
  既知のエンジン側の制限（GDScript同士の循環参照がスクリプトサーバーの
  完全シャットダウンパスでしか解放されないため）であり、本プロジェクトの
  ロジックの不備ではないと判断する。
- **背景**: 第0章は「エラーやワーニングを握りつぶすな」と明確に禁止しているため、
  原因を特定せず無視することは許されない。上記の切り分け（Phase 2 の
  コミット済み状態ではこの現象が発生しないこと、`--verbose` の全リーク行が
  スクリプトリソースのみであること、実際の起動検証コマンド
  `godot --headless --quit-after 100` ではこの現象が一切発生しないこと）を
  行った上での判断である。
- **選択肢**: 1. 原因不明のまま放置する 2. 原因を特定し、実害（実際のゲームプレイ
  オブジェクトのリーク）がないことを立証した上で、CLIツール固有の既知現象として
  文書化する
- **選択理由**: 2 を採用。第8.2章のメモリリークテスト（5分間の自動戦闘後の
  `OBJECT_COUNT`/`MEMORY_STATIC` 監視）は実際のゲームプレイループを対象とすべきであり、
  短命な `--script` CLIプロセスの終了時挙動を代替指標にすべきではない。Phase 8 で
  実際の戦闘ループを回した上での `Performance.get_monitor()` 計測に置き換える。
- **トレードオフ**: `tools/ci_test.sh` の gdUnit4 実行ステップは、このメッセージが
  出力されても CI を失敗させない（実際のテスト結果 PASS/FAIL のみで判定する）。
  将来 gdUnit4 のアップデートやこの Godot エンジン側の既知問題の修正で
  解消される可能性がある。

## ADR-011: Phase 3 のスコープを「戦闘ロジック」に絞り、HUD/VFX/SFX は既知の負債とする

- **決定**: Phase 3 では `WeaponComponent`（発射レート/弾数/リロード/スプレッド/
  決定論的リコイル/ダメージ確定）、`SkillComponent`（クールダウンゲート）、
  `UltimateChargeComponent`（与ダメ/被ダメ/時間経過の3系統加算）を実装しテストで
  検証した。一方で第4.4章が要求する9項目のジューシーネス演出（マズルフラッシュ、
  薬莢排出、ヒットマーカー、ダメージ数値、キルフィード等）と第3.4章のHUD第一版
  （動的レティクル、HPバー、弾薬表示等）は本フェーズでは実装しない。
- **背景**: これらの演出・UI一式は Godot 標準ノード（`GPUParticles3D`/`Control`/
  `ObjectPool` 経由）だけで作成可能ではあるが、実際の見た目・「爽快感」の
  検証にはヘッドレス環境では到達できないビジュアル確認が本質的に必要であり
  （第11章の「体感レビュー」参照）、中途半端な実装を積み上げるより、
  戦闘ロジックそのものの正しさをテストで固めることを優先した。
- **選択肢**: 1. 全9項目を見た目未検証のまま一括で作り切る
  2. サーバー権威のロジック層を先に完成させ、演出層は次の作業単位として
  明確に区切る
- **選択理由**: 2 を採用。第0章「動くだけのコードは成果物ではなく負債」の精神に
  基づき、検証できない演出コードを大量に積むより、テストで裏付けられた
  ロジック層を優先する。
- **トレードオフ**: 現時点でヒーローを実際に操作しても、視覚的なフィードバック
  （マズルフラッシュ・ヒットマーカー・HUD）は得られない。次の作業で
  `tests/perf/` の HUD コスト計測（0.5ms以下）と合わせて実装すること。

## ADR-012: Phase 4 は「決定論的に検証可能な純粋ロジック」を優先し、実ネットワーク往復は次工程とする

- **決定**: Phase 4 では以下を実装・テストした: `InputCommandCodec`（量子化エンコード/
  デコード）、`Reconciliation`（サーバー確定状態とクライアント予測の比較・
  再シミュレーション、`MovementSimulation` と同一コードパスを共有）、
  `ServerValidation`（移動距離・発射間隔のサーバー側検証）、`NetworkComponent`
  （pending_inputs バッファとリコンサイル起点）、`StateSnapshot`。
  一方で、実際に2つ以上の `ENetMultiplayerPeer`（サーバー役/クライアント役）を
  同一プロセス内でループバック接続し、`@rpc` 経由で InputCommand/StateSnapshot を
  往復させる**実ネットワーク統合**、専用サーバー起動スクリプト
  (`godot --headless --server`)、`HeroBase`/`NetService` への実際の RPC 配線は
  本フェーズでは実装しない。
- **背景**: 第9章は「不確かなまま実装したコードは削除して書き直す」ことを求める。
  `@rpc` を用いた実際のクライアント/サーバー往復は、API の存在確認だけでなく
  実際の複数ピア間の挙動（tick同期、RPCの到達順序、authority の伝播）を
  実機で確認しなければ「不確かな実装」のままになる。本セッションはヘッドレスの
  単一プロセス環境であり、複数の Godot プロセス（または複数 SceneTree）を
  同時に起動して実際の ENet 通信を往復させる検証環境を持たない。
- **選択肢**: 1. 実ネットワーク配線コードを検証なしに書き切り「完了」と報告する
  2. 決定論的に検証可能な純粋ロジック（本丸となるリコンサイルアルゴリズムそのもの）
  を先に完成させ、実ネットワーク配線は「要実機検証」の既知の負債として明記する
- **選択理由**: 2 を採用。第0章「動くだけのコードは成果物ではなく負債」および
  第8.4章「原因を特定できない修正を積み重ねない」という方針に従い、
  検証できないRPCコードを大量に書くより、ネットワーク層の心臓部である
  リコンサイル・量子化・サーバー検証ロジックをテストで裏付けることを優先した。
- **トレードオフ**: 現時点では実際に2台のクライアントを接続してマルチプレイ対戦を
  行うことはできない。次アクションとして、実際に `godot --headless --server` で
  起動したプロセスと通常のクライアントプロセスを用意し、
  (1) `NetService.start_server`/`start_client` の実接続、
  (2) `InputCommandCodec` を使った `@rpc` でのコマンド送信、
  (3) `HeroBase` の `NetworkComponent`/`Reconciliation` を実際のサーバー応答に
  接続する配線、(4) 第8.2章の遅延シミュレーション統合テスト（0/60/150/250ms +
  ジッタ30ms + ロス3%）を、実機（人間のレビュー、または複数プロセスを
  起動できる環境）で行う必要がある。
